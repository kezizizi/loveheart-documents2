# 领域文档

工程类 skill 在探索代码库之前，应当怎样消费本仓库的领域文档。

## 探索之前先读这些

**本仓库是单上下文（single-context）仓库，但领域语言不放在 `CONTEXT.md` 里** ——
它已经在交接文档里了，而且只有那一份。请读：

- **`CLAUDE.md` 第 6 节「领域口径」** —— 领域词表（主键 / 部组 / 学期 / 入社日期 /
  学时 / 参与时间 / 感想 / 同行伙伴 / 缓存）。**这就是本仓库的 glossary。**
- **`CLAUDE.md` 第 3 节「不可违反的硬约束」** —— 每条红线后面都写了**为什么**
  （哪次真实事故、哪个用户指令）。这等价于别处的 ADR：动手前先读要碰的那一块。
- **`CLAUDE.md` 第 1.1 与第 4 节** —— 架构与分层（数据层 / 业务层 / 适配层 / 宿主层），
  以及"唯一缝"在哪。
- **`docs/adr/`** —— 目前**不存在**。若将来出现，读与你要动的区域相关的那些。

这些文件不存在时，**静默继续**，不要提示缺失、也不要主动建议创建。
（本仓库刻意只有一个交接文档；再摊开第二份领域文档，两边必然各自演化 ——
今天已经因为这个原因修过两次 bug：前端与后端各算一套派生、旧 UI 与新 UI 各一份部组名单。）

## 用 glossary 里的词汇

产出里凡是要提到领域概念的地方（issue 标题、重构提案、假设、测试名），
都用 `CLAUDE.md` 第 6 节里定义的词。**不要**漂到它刻意回避的同义词上。几个已经踩过的例子：

| 用这个 | 不要用 | 为什么 |
| --- | --- | --- |
| 部组 | 部门 / 小组 / 分组 | 「部组」的判定权唯一在后端（文件夹层级），换个词会让人以为可以前端再判一次 |
| 学期（`2025秋`） | 届 / 期 / 年度 | 格式写错（`23秋`）会让前端学年分组整个塌掉 |
| 同行伙伴 | 同行人数 / 同伴数 | 只出**人数**、不出姓名，别让它听起来像能拿到名单 |
| 活动表 | 分表 / 子表 / 问卷表 | 它的识别规则是「有 link 字段指回主表」，不是按名字或位置 |
| 没查成 / 取数失败 | 查不到 / 未命中 | 这两件事**必须分开**（红线 3.12）：前者是系统问题，后者才是"档案里没有你" |

如果你需要的概念还没进 glossary，那是个信号 —— 要么你在造项目不用的词（再想想），
要么确实有缺口（记下来，用 `/grill-with-docs` 补）。

## ADR 冲突要显式指出

如果你的产出与某条既有红线（或未来的 ADR）冲突，**显式说出来**，不要默默绕过：

> _与红线 3.1（只访问主表已关联的活动表）冲突 —— 但值得重新讨论，因为……_

反过来也一样：**如果你要改红线，必须同时改 `CLAUDE.md` 第 3 节**，
它是这个仓库里唯一的口径来源。
